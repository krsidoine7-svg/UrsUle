## 1. Diagnostic & Problème d'Authentification (Migration 022)
* Exécution du script de test database (`scratch_test_db.ts`) révélant une erreur d'authentification bloquante :
  * Erreur : `Database error saving new user` lors de l'inscription via GoTrue.
  * Cause : La fonction trigger `handle_new_user()` s'est vu révoquer ses droits d'exécution de `PUBLIC` (y compris `anon`), mais les droits d'exécution n'ont pas été explicitement accordés au rôle système `supabase_auth_admin` qui exécute l'insertion.
* Résolution (Migration 022) :
  * Correction du `search_path` de `purge_trash_tasks` et `handle_new_user`.
  * Révocation générale des droits d'exécution sur les fonctions de soft-delete, notifications, récurrence, etc. du rôle `PUBLIC` pour empêcher leur appel direct par API REST/RPC.
  * Attribution explicite de l'exécution sur `handle_new_user()` et `set_admin_on_signup()` à `supabase_auth_admin` pour débloquer les inscriptions.
  * Durcissement des politiques RLS de 17 tables en spécifiant explicitement `TO authenticated` (évite les avertissements du linter Supabase concernant l'accès anonyme).
  * Sécurisation de l'exécution des fonctions en les empaquetant dans un bloc `DO $$` pour éviter des erreurs PostgreSQL si certaines fonctions (`set_admin_on_signup` ou `purge_trash_tasks`) ne sont pas encore présentes sur le serveur.
* L'utilisateur a appliqué avec succès le script de migration sur la base distante.
* Validation par script de test (`scratch_test_db.ts`) : 100% OK.
* Diagnostics `scratch_diagnose.ts` : accès anonyme bloqué comme prévu (RLS en place).
